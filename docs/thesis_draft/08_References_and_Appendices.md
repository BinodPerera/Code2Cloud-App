# APPENDIX B: SYNTHESIZED JINJA2 WORKFLOW AND TEARDOWN TEMPLATES

This appendix details the exact Jinja2 template definitions implemented in Code2Cloud to dynamically render cloud infrastructure and teardown workflows. The templates demonstrate how declarative HCL blocks, containerization commands, and GitHub Actions orchestration routines are parameterized without sacrificing syntactic rigor.

### B.1. Automated Cloud Teardown Workflow Template (`aws_destroy.jinja`)

The following template definition, stored in `backend/app/modules/generation/templates/workflows/aws_destroy.jinja`, dynamically generates the GitHub Actions pipeline responsible for destroying provisioned cloud resources:

```jinja
name: Destroy {{ cloud_provider | default("AWS") }} Cloud Infrastructure (Teardown)

on:
  workflow_dispatch:
    inputs:
      confirm_destroy:
        description: 'Type "DESTROY" to confirm permanent deletion of all cloud resources'
        required: true
        default: 'DESTROY'

jobs:
  teardown:
    name: Teardown {{ cloud_provider | default("AWS") }} Cloud Resources
    runs-on: ubuntu-latest
    if: {% raw %}${{ github.event.inputs.confirm_destroy == 'DESTROY' }}{% endraw %}
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Configure Cloud Provider Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: {% raw %}${{ secrets.AWS_ACCESS_KEY_ID }}{% endraw %}
          aws-secret-access-key: {% raw %}${{ secrets.AWS_SECRET_ACCESS_KEY }}{% endraw %}
          aws-region: {{ aws_region | default("us-east-1") }}

      - name: Setup Terraform CLI
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.5.7

      - name: Initialize Terraform Working Directory
        run: terraform init
        working-directory: ./terraform

      - name: Execute Automated Resource Destruction
        run: terraform destroy -auto-approve
        working-directory: ./terraform
```

### B.2. Core AWS Terraform Infrastructure Template (`aws_main.jinja`)

The following template snippet demonstrates how `service_generator.py` parameterizes EC2 instances, security groups, and ingress firewall rules:

```jinja
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}

resource "aws_security_group" "app_sg" {
  name        = "{{ app_name }}-sg"
  description = "Security group for {{ app_name }} managed by Code2Cloud"
  vpc_id      = var.vpc_id

  ingress {
    description = "Application Ingress Port"
    from_port   = {{ app_port }}
    to_port     = {{ app_port }}
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    description = "Allow all outbound traffic"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name        = "{{ app_name }}-sg"
    Environment = "Production"
    ManagedBy   = "Code2Cloud"
  }
}

resource "aws_instance" "web_app" {
  ami           = var.ami_id
  instance_type = "{{ instance_type }}"
  key_name      = var.key_name

  vpc_security_group_ids = [aws_security_group.app_sg.id]

  user_data = <<-EOF
              #!/bin/bash
              yum update -y
              yum install -y docker
              systemctl start docker
              systemctl enable docker
              docker run -d -p {{ app_port }}:{{ app_port }} {{ docker_image_tag }}
              EOF

  tags = {
    Name        = "{{ app_name }}-instance"
    ManagedBy   = "Code2Cloud"
  }
}
```
